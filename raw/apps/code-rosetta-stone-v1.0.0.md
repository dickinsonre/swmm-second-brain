# SWMM5 Rosetta Stone: compare water-modeling code and run labeled numerical engines

## What it does

This app helps water-modeling developers compare SWMM and EPANET algorithm examples across programming languages.
It also runs uploaded SWMM input models through explicitly identified numerical engines or EPA-core adapters.
It returns simulation reports, execution provenance and result metadata.
Educational demonstrations, source viewing, quizzes and an AI chat are separate from numerical-engine validation.

Metadata sources: display name in `src/App.jsx:1268`; package version in `package.json:2-4`; repository in `git remote -v`; published URL from the deployment metadata query made for this summary.

## How it computes

1. The comparison viewer reads illustrative algorithm strings from `src/modules.js` and `src/epanetModules.js`. Displaying a translation does not execute or validate it.
2. `registerSwmmRoutes` in `server/swmm-routes.js:9-25` receives a model and dispatches the selected registry entry to `simulate`.
3. `simulate` in `server/swmm-runtime.js:144-188` chooses the independent subset, imported translation or pinned EPA core. It rejects unsupported selections and escaping external-file paths.
4. `inspectImported` and `simulateImported` in `server/github-runtime.js:11-66` verify source/build hashes, create a temporary model directory and execute the selected language program with input, report and output paths. There is no numerical fallback to EPA.
5. The EPA driver calls `swmm_run` directly in `bindings/core-main.c:5-11`. Language adapters invoke this same solver; they are interfaces, not independent numerical implementations.
6. A concrete translated lifecycle is `Project::swmm_run`, `Project::swmm_step` and `Project::execRouting` in `engines/github/swmm5-cplus/src/engine/swmm5.cpp`. The lifecycle advances runoff and routing through `runoff_execute` and `routing_execute`; see lines 201-242, 425-477 and 524-577.
7. The Python subset uses `parse` in `solver/python_native/parser.py` to enforce supported storage/outlet inputs. `integrate` in `solver/python_native/engine.py:23-33` solves `dV/dt = rate + slope*t - decay*V` analytically. `simulate`, lines 36-133, computes depth as volume/area, accumulates outflow and checks `residual = initialStorage + inflow - outflow - finalStorage`.
8. Independent browser demonstrations use their own simplified equations. They are not the imported numerical ports.

Examples of browser calculations, transcribed from their named functions:

| Calculation | Implemented equation or operation | Source |
|---|---|---|
| Section geometry | `R = A / wettedPerimeter`; rectangular `A = width*depth`; trapezoidal `A = depth*(bottom + sideSlope*depth)` | `calcCircular`, `calcRectangular`, `calcTrapezoidal`, `calcTriangular`, `src/apps/CrossSectionCalc.jsx:10-45` |
| Illustrative pipe flow | `Q = A*R^(2/3)*sqrt(slope)/n`; explicit node-depth update from net inflow | `manningFlow`, `simulateStep`, `src/apps/MicroEngine.jsx:20-47` |
| Illustrative runoff | `S = 1000/CN - 10`; `Ia = 0.2*S`; excess rain `(P-Ia)^2/(P-Ia+S)` above abstraction, then convolution with a synthetic unit hydrograph | `generateRunoff`, `src/apps/HydrographPlotter.jsx:47-80` |
| Illustrative design storm | `i = a*(0.5 + 0.5*log(T)/log(10))/(duration+b)^n`; incremental depths sorted into alternating blocks | `getIntensity`, `generateAlternatingBlock`, `src/apps/DesignStormGen.jsx:16-48` |
| Illustrative uncertainty | Random parameter sampling followed by simplified Manning capacity, peak-flow summaries and flooding frequency | `runMonteCarlo` and component `run`, `src/apps/UncertaintyLab.jsx:3-53` |

The runoff example uses inches for precipitation. Section examples display feet and square feet. The numerical subset returns cubic feet and feet for US flow-unit models, or cubic meters and meters for SI models (`solver/python_native/engine.py:127-129`).
The MicroEngine formula is reported as implemented, not corrected to a US customary Manning coefficient. Its dimensions and numerical fidelity are not certified here.

## Inputs and outputs

- Read: uploaded `.inp` models and bundled `.inp` examples; source text for viewing; JSON chat messages.
- `GET /api/engines`: engine identities, local availability and provenance.
- `POST /api/run-swmm` and registry-defined `/api/run-swmm-*` routes: multipart `inpFile`; report text and JSON result/provenance. The subset supports preflight requests.
- `GET /api/engine-source/:lang` and `GET /api/educational-source/:id`: source text. Unsupported run routes return an explicit unavailable response.
- `POST /api/chat`: streams Anthropic text as server-sent events (`server/chat-routes.js:15-34`).
- Simulation processes write temporary `.inp`, `.rpt` and `.out` files. Cleanup is in `finally` blocks in `server/github-runtime.js:42-66` and `server/swmm-runtime.js`.
- The runner offers report `.rpt` and subset `.results.json` downloads (`src/apps/SwmmEngineRunner.jsx:3742-3748,4042`). An internally created binary `.out` is not proof of a binary-download feature.
- UI selections, uploaded model text and displayed results use React state. No database-backed persistence path was found in the inspected server entry and route modules.
- Upload memory limits are 50 MiB and one file per request (`server/swmm-routes.js:7`). Default process timeout is 120 seconds (`server/swmm-runtime.js:144`).

## How to reproduce

Use the toolchains declared in `.replit` and dependencies declared in `package.json` and `pyproject.toml`.
The development command builds or verifies available engines, starts Express and starts Vite (`package.json:7-14`). The backend listens on port 3001 and Vite on port 5000 (`server.js:9`; `package.json:9`).

```sh
npm ci
python3 scripts/import-github-engines.py
npm run dev
```

In another shell, after the app is ready:

```sh
node --test tests/*.test.mjs
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'test_python_native.py' -v
node --experimental-websocket tests/github-ui-smoke.mjs
```

The API suite requires `ENGINE_AUDIT_URL` or the development-domain setting used by `tests/engine-api.test.mjs:8-9`.
The browser smoke script requires Chromium and writes screenshot evidence. Port tests also write evidence files. This review redirected test-generated evidence outside the project.
Use `npm run build:ports` for an explicit port build and `npm run build` for the configured production build. Building frontend assets alone does not deploy the Express API.
